* Introduction to Bootstrap Common Lisp -- BOCL.

(From Robert Strandh)

BOCL is (meant to one day be) a fully conforming Common Lisp
implementation with a twist.  It is only meant for bootstrapping other
Common Lisp implementations on platforms where, for some reason, no
Common Lisp implementation is already available.  It is not meant for
writing end-user applications.

This main purpose of BOCL has some consequences to the way it is
implemented.  In particular, there is no attempt to make it fast, or
frugal in memory.

Instead, the emphasis is on simplicity, maintainability, and
correctness.

- BOCL is implemented ISO C =ISO/IEC 9899:2018= ("C17"), targetting
  POSIX platforms.  We avoid to use constructs with undefined
  semantics, as the C standard indicates.  Only readily available
  shell tools are used in order to maximize portability.

- We implement a simple mark-and-sweep garbage collector.

- We take advantage of all situations in which the Common Lisp
  standard states that some behavior is undefined or implementation
  defined, in that we then do whatever is the easiest solution for the
  situation.

- The type FIXNUM does not have a corresponding class.  All integers
  are represented the same way.

- All objects have the same basic representation as a header
  containing a pointer to the class of the object and a pointer to a
  vector (not a Common Lisp vector) with the objects-specific
  contents.

- The only specialized arrays are those mandated by the Common Lisp
  standard, and even those arrays do not use any special
  representation.  The only exceptions are STRING vectors that are
  specialized using octets to store the characters, and BIT-VECTOR
  that use the same representation (storing one bit per octet).
  Since the target platforms provide octet-based file accesses and
  system interfaces, this leds to simplified interface.

- More generally, we make no attempt to save space.

- All higher level data structures such as hash-tables, packages, CLOS
  classes, are implemented in Lisp.

- There is no attempt to handle tail-call merging.

- All functions are called with a Common Lisp list of arguments.

Currently, several free (or, more generally, FLOSS) implementations of
Common Lisp are built from sources in some other language.  That
language is typically C, but sometimes something else, like C++.
There are probably several reasons for these implementations to be
written this way, including historical (there was no widespread
existing Common Lisp implementation when they were written), limited
knowledge (the author did not know how to write a Common Lisp
implementation in Common Lisp), and more.

The process of building a Common Lisp system from sources written in
some other language is a painful one, especially if one of the main
objectives is for it to be fast, safe, and helpful to the programmer.
Large parts of the system must be written in a language that is not
very well adapted to expressing the semantics of Common Lisp.  Even
though large parts of the system can be written in Common Lisp,
because of the way the system is built, many system modules must be
written in a subset of Common Lisp, making also that part painful to
write.  For instance, it is common that CLOS not be available until
very late in the bootstrapping process.

The existence of BOCL will relieve most of the pain of maintainers of
Common Lisp systems by concentrating that pain into BOCL.  These
maintainers can now migrate their code from the existing
implementation language to Common Lisp, relying on BOCL to exist.  At
the same time, there is considerably less pain because of the
simplifications to BOCL listed above.

As an exception to the goal of simplicity, BOCL will contain a full
implementation of the CLOS meta-object protocol (MOP) so as to allow
implementers of other Common Lisp systems to take advantage of the MOP
in their own implementations.

In addition to being a bootstrapping tool for Common Lisp
implementers, we think that BOCL will be an excellent illustration of
the semantics of Common Lisp.  To make it easier for people interested
in that topic, we think it is important that the BOCL code be highly
idiomatic, uniform, and well documented.

BOCL will not happen unless it is contributed to by others, so if you
have knowledge of how to implement Common Lisp in C or interest in
learning how to do it, please consider contributing.

** Error handling: the =--on-error= option

The =--on-error= option selects what bocl does when an
/unhandled/ =SERIOUS-CONDITION= reaches the top level --- that is, an error your own
code did not catch with =HANDLER-CASE=, =IGNORE-ERRORS=, or a restart.  The action
is published to Lisp as =BOCL:*ON-ERROR*=.  There are four actions.  When
=--on-error= is /not/ given, option processing, the init/rc files and =-l= / =-x=
forms run under =exit= (fail hard, good for batch), while the interactive REPL
instead defaults to =debug=.

An =--on-error= given /before/ the first =-i= (or =--no-init=) sets the policy used
to load the rc and init files; one given /after/ the first =-i= is processed in
command-line order together with the =-l= / =-x= forms --- it behaves exactly like
=-x '(setf bocl:*on-error* ACTION)'= and applies to everything that follows it
until the next =--on-error=.  The init files may themselves =setf= =*on-error*=,
which takes effect immediately for the following forms.  If any =--on-error= is
given, the REPL uses the last value in effect; otherwise it defaults to =debug=.

| Action    | At the REPL (unhandled error in a typed / =-x= form)        | While LOADing a file (rc, =-i=, =-l=, nested loads)              |
|-----------+-------------------------------------------------------------+-----------------------------------------------------------------|
| =exit=    | Report the condition and exit the process (status 1).       | The error aborts the load; the process exits.                   |
| =debug=   | Enter the interactive debugger (=INVOKE-DEBUGGER=): banner,  | The failing form drops into the debugger.                       |
|           | backtrace, restart menu, debug REPL.                        |                                                                 |
| =abort=   | Report the condition and return to the top-level REPL        | The failing form aborts the whole load.                         |
|           | (no debugger; the process stays alive).                     |                                                                 |
| =appease= | Same as =abort= (report and return to the prompt).          | Per-form recovery: the failing top-level form is reported       |
|           |                                                             | (=;; [load] skipped a form: ...=) and skipped, and loading      |
|           |                                                             | continues (skips are counted in =*LOAD-ERROR-COUNT*=).          |

The essential distinctions:

- =exit= is the fail-hard mode for batch / scripts / CI: any uncaught error stops the
  process with a non-zero status.  The other three keep the session alive.
- =debug= versus =abort=: both keep you alive, but =debug= opens the debugger to inspect
  the backtrace and choose a restart, whereas =abort= simply unwinds back to the prompt.
  =debug= is the natural choice for interactive development.
- =abort= versus =appease=: identical at the REPL; they differ only for =LOAD=.  =abort=
  aborts the whole file on the first bad form, while =appease= skips bad forms and loads
  everything it can --- intended for loading large or partially-supported suites (e.g.
  the SACLA / ANSI tests) so they reach their final report instead of dying on the first
  unsupported form.

The minimal debugger entered by =debug= is described in
=debugger-specifications.org=.

** 3. Evaluation and Compilation


The C kernel provides an =EVAL= interpreter (no virtual machine or
byte-code compiler).  "Compilation" in bocl means *minimal
compilation* (CLHS 3.2.2.2): macro and symbol-macro calls are expanded
so the resulting code contains only special operators and function
calls.

- =MACROEXPAND-1=, =MACROEXPAND= and =MACROEXPAND-ALL= are provided.
  =MACROEXPAND-ALL= is the minimal-compilation code walker: it returns
  a macro-free form, leaving quoted data, binding-form variable lists
  and =(THE type ...)= type specifiers untouched while walking every
  evaluated subform.

- =COMPILE-FILE= reads each top-level form, runs =MACROEXPAND-ALL= on
  it, and writes the macro-free forms to a *fast-load* file (default
  file type from =*DEFAULT-COMPILED-FILE-TYPE*=, "fasl").  =LOAD= of a
  fast-load file is faster because no macro expansion is needed.

- At run time the interpreter performs *macro displacement*: the first
  time a global-macro call form is evaluated it is replaced in place by
  its expansion, so the expansion (and any =GENSYM= / backquote consing
  it entails) happens once, not on every evaluation.  This gives
  interpreted code most of the benefit of minimal compilation without a
  separate compile step.

Interpreter performance notes (implementation specific):
- =S(symbol)=-style kernel symbol references are cached per call site
  (they were re-interned on every use, which dominated eval time).
- The package obarray is indexed by a hash table, so the reader interns
  symbols in O(1) rather than O(n) per symbol.
- A cons cell is a single 32-byte object (class, car, cdr inline)
  rather than an object plus a separate slots block.

** 3.4 Lambda List

The initforms in the lambda lists are evaluated only when needed,
(when the argument is absent).

However, their expressions are macro-expanded during the compilation
(minimal-compilation) macro-expansion phase.

The &key parameters are bound in the order of appearance,
independently of the order of the key value pairs in the argument
list.  Only the first occurence of a given key is used in the argument
list.

** 19. Filenames

A logical pathname implementation can be obtained from
com.informatimago/future/vfs/filenames.lisp

The kernel implements a physical-pathnames wrapper (posix paths).

Pathnames print readably: =PRIN1=/=PRINT= write =#P"namestring"=, and
=PRINC= writes the bare namestring (for both physical and logical
pathnames).

Configurable file types (implementation specific) drive file lookup:
- =*ACCEPTED-SOURCE-FILE-TYPES*= — types tried to find a source file
  given a typeless pathname (default: "lisp" / "LISP" and
  case-insensitive "lisp", "lsp", "cl", "l").
- =*ACCEPTED-COMPILED-FILE-TYPES*= — types tried to find a compiled
  file (default: "fasl" / "FASL" and case-insensitive "fasl", "fas",
  "obj", "o").
- =*DEFAULT-COMPILED-FILE-TYPE*= — the type =COMPILE-FILE= gives its
  output when none is specified (default "fasl").
An element may be a string (case-sensitive) or =(:case-insensitive
"type")= to force a case-insensitive search with "type" tried first.

Remains to implement the generic pathname functions, pathname
translations, and to wire the full type-based file-selection logic
into =LOAD=.

multi-file CL library.)

We may implement in CL a =COMPILE-FILE= performing at least the
minimal-compilation saving the result in "fasl" files.

The variables must be defined and used where relevant (=LOAD=,
=COMPILE-FILE=, =#+/#-= etc).

*** Function BOCL:VALIDATE-CFASL

: (bocl:validate-cfasl path &key (report t) (stream *standard-output*))
:   -> (values valid-p form-count message version)

Structurally validate the compiled fasl (=.cfasl=) file at =PATH=
without evaluating anything from it: the =BOCLFASL= magic, the format
version, that every top-level form reads back through the cfasl
reader, and that the image ends with the end-of-image tag as its
final byte.  When =REPORT= is true (the default), a one-line verdict
is printed to =STREAM=.  =VALID-P= is =T= when every check passes;
=FORM-COUNT= is the number of top-level forms that read cleanly;
=MESSAGE= is a string naming the first problem (or =NIL=); =VERSION=
is the image's format version (or =NIL= when the header is
unreadable).

Validation is independent of the session's package state: a symbol in
a package that the image itself would create (a =DEFPACKAGE= in an
earlier form, which validation deliberately does not evaluate) reads
as an uninterned placeholder instead of failing.

A truncated or corrupt boot image is already rejected automatically
(with a warning and a fallback to the source); this function is the
explicit inspection tool that says /what/ is wrong with an image:

: bocl> (bocl:validate-cfasl "bootstrap/prelude.cfasl")
: ;; bootstrap/prelude.cfasl: valid cfasl (format v2, 1166 top-level forms).
: T
: 1166
: NIL
: 2

** The KERNEL Package

The core of the =bocl= implementation is written in C, with a limited
set of primitive and restricted operators, that are exported from the
KERNEL package.

The KERNEL package is not intended to be used by end-user of the
=bocl= implementation.  Instead, it is used by =bocl= to implement a
fully conforming Common-Lisp.

The kernel provides:

- a garbage collected heap of fundamental lisp objects.

- fundamental functions for the fundamental lisp objects.

- an =EVAL= function.  The =EVAL= function implements the fundamental
  special operators.

- a few functions needed to load the =bocl= Common-Lisp implementation:
   + a tiny lisp reader,
   + a tiny lisp printer,
   + a file loader,
   + etc.

- basic error handling.

- two symbol tables: one for the kernel symbols, and one for keywords
  (self valued).  We need keywords to read Common-Lisp sources.

- a few operators to define objects in toplevel forms.

- platform functions such as I/O, environment, etc, that couldn't be
  implemented in conforming Lisp.

** The Garbage Collector
*** Function ID

Syntax:

    ID (object) => id

Arguments and Values:

    object -- a lisp object

    id -- an integer

Description:

    The unique ID of the object could be its address converted to
    integer, if the garbage collector is not moving the objects, or a
    cached unique integer if the garbage collector may move the
    object.  The ID of an object won't change while the object is
    alive.

Result:

    Returns a unique ID of the object.

*** Function GC

Syntax:

    GC (&optional command) => state

Arguments and Values:

    command -- NIL, :ON or :OFF

    state -- an integer or :ON or :OFF

Description:

	If `command` is NIL, the garbage collector is called now.
    If `command` is :ON then the garbage collector is enabled (initial
    state).
    If `command` is :OFF then the garbage collector is disabled.

Results:

    If `command` is NIL, then the number of bytes collected.
    If `command` is :ON or :OFF, then the previous state of the
    garbage collector.

** External-format

External-formats can be:

- :DEFAULT in place of (:iso-8859-1 :lf :error)

- a keyword denoting an encoding in (:us-ascii :iso-8859-1);
  the default line-termination is :lf, and
  the default encoding error handling is :error (signal an error).

- a list containing:

  + a keyword denoting an encoding in (:us-ascii :iso-8859-1),

  + a line-termination keyword (:dos :crlf :mac :cr :unix :lf),
    the default if NIL or absent is :LF.

  + an object specifing the handling of encoding errors:

    * a character used as substitution character #\sub is suggested,
      or an integer used as substitution code 26 (SUB) is suggested.
      (code-char code) is used on input encoding error.
      (char-code char) is used on output decoding error.

    * the keyword :error asking for a continuable encoding-error to be
      signaled, with a substitute-code restart. This is the default if absent.

    * the symbol NIL asking to ignore and skip the unencodable
      character.

Encoding or decoding errors can only occur with a code>127 given with
:us-ascii, since we deal only with :us-ascii (7-bit) and :iso-8859-1
(8-bit) and internal coding is iso-8859-1.


Note: kernel:stream-external-format accept only (:crlf :cr :lf) as
line-termination; the mapping is done in the CL layer.


Unicode and UTF-8 is out of scope for version 1.

#+BEGIN_EXAMPLE
(:us-ascii :crlf #\SUB)     Write the #\SUB character instead.
(:us-ascii :crlf :error)    Signal an error.
(:us-ascii :crlf nil)       Ignore and skip the invalid character.
#+END_EXAMPLE

** The REPL

The REPL is a standard REPL.

*** The prompt: BOCL:*PROMPT-FUNCTION*

=BOCL:*PROMPT-FUNCTION*= is =NIL=, or a function designator of one argument (an
output stream).  When it is non-=NIL= the REPL calls =(funcall
bocl:*prompt-function* stream)= to write each prompt, instead of the default
=bocl>= prompt.  Binding or setting it (typically from an init file) lets a
program customise the prompt — e.g. show the current package, an input counter, or
the debug level.

*** Init (rc) files

Unless =-n= / =--norc= / =--no-init= is given, bocl loads at most one init
file at start-up, the first that exists from this list (a leading =~/= is
the user's home directory, =(USER-HOMEDIR-PATHNAME)=):

| order | file                              |
|-------+-----------------------------------|
|     1 | ~~/.bocl~                         |
|     2 | ~~/.bocl.fasl~                    |
|     3 | ~~/.bocl.lisp~                    |
|     4 | ~~/.boclrc~                       |
|     5 | ~~/.boclrc.fasl~                  |
|     6 | ~~/.boclrc.lisp~                  |
|     7 | ~~/.config/bocl/init~             |
|     8 | ~~/.config/bocl/init.fasl~        |
|     9 | ~~/.config/bocl/init.lisp~        |
|    10 | ~~/.common-lisp~                  |
|    11 | ~~/.common-lisp.fasl~             |
|    12 | ~~/.common-lisp.lisp~             |
|    13 | ~~/.config/common-lisp/init~      |
|    14 | ~~/.config/common-lisp/init.fasl~ |
|    15 | ~~/.config/common-lisp/init.lisp~ |

This is the union of bocl's historical init-file locations (the =~/.bocl=,
=~/.config/bocl/init=, =~/.common-lisp= and =~/.config/common-lisp/init= stems)
and the per-stem =bare= / =.fasl= / =.lisp= variants.  The first match wins,
except that when the match is a =.fasl= whose =.lisp= sibling exists and is more
recent, the =.lisp= is loaded instead (the fasl is stale).  After the init file,
every =-i= / =--init= file given on the command line is loaded in turn.  Then the
functions on BOCL:*INIT-HOOK* are called.  Then the main task runs (=-x= / =-l=
forms and the REPL).

*** Function BOCL:QUIT

Syntax:

    BOCL:QUIT (&optional (status 0)) => non-local-exit

Arguments and Values:

    status -- an integer (default 0)

Description:

    Exits the =bocl= process with the given STATUS.  QUIT performs a
    /non-local exit/, so any UNWIND-PROTECT clean-up clauses pending in
    the current dynamic environment are run on the way out.  Being the
    primitive used by WITH-OPEN-FILE and similar resource macros, this
    lets them close and free their resources (flush buffers, close
    files and sockets) before the process exits.

    Once the dynamic environment has been unwound, the functions on
    BOCL:*QUIT-HOOK* are each called (inside IGNORE-ERRORS), and then
    the process exits.  QUIT does not return.

*** Extension hooks

Five lists of function designators let user code (typically from the
init/rc file, a -i file, the command line, or normal Lisp code) run
code at well-defined points in the process life-cycle.  They live in
the BOCL package and are never cleared (a function on a list serves
until removed by the user).  No locking is provided.

| variable          | signature        | when called                                            |
|-------------------+------------------+--------------------------------------------------------|
| BOCL:*INIT-HOOK*  | (lambda ())      | after the rc/init file has been loaded (or --no-init   |
|                   |                  | processed), before the main task (-l/-x/-i + the REPL) |
| BOCL:*QUIT-HOOK*  | (lambda (status))| by BOCL:QUIT, after the non-local exit unwinds the     |
|                   |                  | dynamic environment, just before the process exits     |
| BOCL:*ABORT-HOOK* | (lambda (signum))| when the process is crashing on a fatal signal; the    |
|                   |                  | GC is disabled and the heap may be corrupt             |
| BOCL:*STOP-HOOK*  | (lambda ())      | on SIGTSTP (Ctrl-Z), before the process suspends —     |
|                   |                  | e.g. reset the terminal out of raw/ncurses mode        |
| BOCL:*CONT-HOOK*  | (lambda ())      | on SIGCONT, when the process resumes — e.g. re-enter   |
|                   |                  | raw mode or re-open what *STOP-HOOK* released          |

Each function on a hook list is called in turn, each wrapped in an
IGNORE-ERRORS.  If a hook calls BOCL:QUIT, or a crash occurs, the
corresponding processing happens and the remaining functions on the
list are not called.

*INIT-HOOK* and the main task run under a single top-level CATCH for
QUIT, so a QUIT from an init hook, a loaded form, or the REPL is a
proper non-local exit.

*ABORT-HOOK* is best effort, with no guarantees: the signal may
indicate system corruption, so the garbage collector is disabled and
hooks should perform minimal allocation (flush a buffer, write a
dirty/clean flag) and return quickly — the user may otherwise kill an
unresponsive process, preventing the remaining hooks from running.
QUIT-HOOK and ABORT-HOOK functions may be called from a thread other
than the main thread; the main thread starts the main task only once
the INIT-HOOK functions have completed.

** The debugger

When an unhandled =SERIOUS-CONDITION= reaches the REPL and =BOCL:*ON-ERROR*= is
=:debug= (the default — see [[Error handling: the =--on-error= option]]), bocl
enters an interactive debugger on =*DEBUG-IO*=.  It prints the condition, a
backtrace (innermost frame first) and the menu of available restarts, then loops
reading commands at a =debug>= prompt:

| command           | effect                                                       |
|-------------------+--------------------------------------------------------------|
| =:backtrace=      | print the backtrace (accepts options, e.g. a frame count)    |
| =:restarts=       | reprint the restart menu                                     |
| =:restart N¦name= | invoke restart N (or by name); a bare number does the same   |
| =:continue=       | return =NIL= from the debugger and resume                    |
| =:abort=          | invoke the =ABORT= restart — unwind to the top-level REPL     |
| =:quit=           | exit bocl (=BOCL:QUIT=)                                       |
| =<form>=          | evaluate =<form>= in the error's dynamic context, print values |

=INVOKE-DEBUGGER= honours =CL:*DEBUGGER-HOOK*=.  An error while /reading/ or
handling a debugger command does not abort the process: it enters a *nested*
debugger level (recursive debugging, CLHS 9.1), and =:abort= / =:continue= there
return to the enclosing level.

The debugger binds the standard printer variables around its own output from the
=BOCL:*DEBUGGER-PRINT-…*= variables, so a huge or circular condition or backtrace
prints readably without disturbing the user's =*PRINT-…*= settings:

| variable                             | default  | binds                  |
|--------------------------------------+----------+------------------------|
| =BOCL:*DEBUGGER-PRINT-LENGTH*=        | 8        | =*PRINT-LENGTH*=       |
| =BOCL:*DEBUGGER-PRINT-LEVEL*=         | 3        | =*PRINT-LEVEL*=        |
| =BOCL:*DEBUGGER-PRINT-LINES*=         | 2        | =*PRINT-LINES*=        |
| =BOCL:*DEBUGGER-PRINT-CIRCLE*=        | T        | =*PRINT-CIRCLE*=       |
| =BOCL:*DEBUGGER-PRINT-RIGHT-MARGIN*=  | 72       | =*PRINT-RIGHT-MARGIN*= |
| =BOCL:*DEBUGGER-PRINT-CASE*=          | :UPCASE  | =*PRINT-CASE*=         |
| =BOCL:*DEBUGGER-PRINT-BASE*=          | 10       | =*PRINT-BASE*=         |
| =BOCL:*DEBUGGER-PRINT-{ARRAY,ESCAPE,GENSYM}*= | T | the matching =*PRINT-…*= |
| =BOCL:*DEBUGGER-PRINT-{PRETTY,RADIX,READABLY}*= | NIL | the matching =*PRINT-…*= |

When =BOCL:*ON-ERROR*= is =:appease= or =:abort= the condition is reported and the
=ABORT= restart is invoked instead of entering the debugger; =:exit= reports and
exits with status 1.  A =STORAGE-CONDITION= (e.g. control-stack exhaustion) is
always reported and aborted rather than debugged, since the debugger cannot run on
a near-exhausted stack.

** Modules

bocl provides the CL module facility (=PROVIDE= / =REQUIRE=) plus a small
name-based registry, so that =(require :name)= finds and loads an installed module
without the caller knowing its files.

=(PROVIDE module-name)= records MODULE-NAME (a string designator) on =CL:*MODULES*=
(also =BOCL:*MODULES*=) and returns it.  =(REQUIRE module-name &optional
pathnames)= loads a module unless it is already present in =*MODULES*=:

- with PATHNAMES (a pathname or list of pathnames), those files are loaded;
- otherwise the module is looked up /by name/ in the boot-time registry
  =BOCL:*MODULE-LIST*= and its files are loaded.  If no such module is known, an
  error of type =BOCL:UNDEFINED-MODULE-ERROR= is signalled, whose report names the
  module requested, the modules directory that was searched, and the modules that
  /were/ found there.

*** The module search path

At start-up bocl scans a /modules directory/ for module manifests.  Every
sub-directory that contains a =module.manifest= — a plist =(:name "NAME" :files
("abs-namestring" …))= — contributes one entry to =BOCL:*MODULE-LIST*=.  The
manifest =:name= selects the module; the sub-directory name is /not/ significant
(so =modules/asdf3/= may provide the module ="ASDF"=).

The modules directory is resolved by the kernel primitive
=%DEFAULT-MODULES-DIRECTORY=, /independently/ of =argv[0]= or the current directory
— bocl never derives resource locations from the executable path:

1. the environment variable =$BOCL_MODULES_DIR=, if set; else
2. =<dir of the build-configured prelude>/modules/= — this carries the install
   =PREFIX=, so =make install PREFIX=/foo/bar= bakes =/foo/bar/…/bocl/modules/=;
   else
3. the first that exists of the three standard install locations — the same three
   searched for the prelude: =/opt/local/libexec/bocl/modules/=,
   =/usr/local/libexec/bocl/modules/=, =/usr/libexec/bocl/modules/=.

The resolved value is kept in =BOCL:*MODULES-DIRECTORY*=.
