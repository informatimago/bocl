* Memory Management
** Structure

The memory is structured into zones that are allocated with standard C
=malloc()=.   The default zone size is 16MB-16B (allocate slightly
less than 16 MB to let =malloc()= round up to an integral number of
pages).

When we need to allocate bigger objects, we create a bigger zone to
accomodate that big object.

(But currently =ARRAY_TOTAL_SIZE_LIMIT= is 32768 so the biggest object
size is 262144 bytes, well within the default zone size).

Each zone has a header, followed by blocks, to fill the zone.  The
blocks are either free blocks or allocated blocks.  The free blocks of
a zone are chained in a free block list referenced from the zone
header.  The free list is sorted by increasing block size.


To allocate a block, we search for a best fit amongst all the zones.

If an exact fit is found in the free lists, it's allocated.

If the best fit is bigger (and big enough to be split), then it's
split (from the end), reducing the free block, and allocating the new
block.

If no free block big enough are available, the garbage collector is
invoked to free some more space.  If no new free block big enough are
available, a new zone is allocated and the block is allocated in the
new zone.

When freeing a block, if it's followed by a free block, they're
fusionned.  Eventually we'd also want to merge with a previous free
block, but to identify it we'll have to walk the free-list.

To find easily if the previous block is a free block would require
either more overhead (either in the block header, or with a block
trailer), or at last, a bit in the block header that would be updated
depending on the status of the previous block (thus we'd know when
it's worth searching the free list).

** Garbage Collector

The garbage collector is a simple mark-and-sweek garbage collector.

Unfortunately, there may be references from blocks in one zone to
another, so we cannot process the zones independently; (we'd need a
copying garbage collector to help with that).


The mark bit is stored as the most-significant-bit of the objcount
block header field. This bit can be set only during garbage
collection.

*** Finalizer

Some objects may reference external resources (eg. =FileStream_slots=
has a =FILE*= member).  Thos external resources may need cleanup when
the object is garbage collected.  Therefore we need to attach a
finalizer function to some blocks.

To indicate that a finalizer is present, the second
most-significant-bit of the objcount is set.

*** The rootset problem

The garbage collector needs to know the rootset.  The rootset is a
given block, which can contain further references to other live
blocks.  The kernel builds it as a list (cons-chain) of lisp objects
that we want to retain.

This rootset must be augmented dynamically with the temporary objects
that live in the C functions stack frames (temporary local variables),
or the garbage collector needs to be disabled until those objects  are
dead or added to the rootset list.

For lisp functions (interpreted), the environment will be lisp objects
linked from the rootset.

We could use a system similar to Auto-Release Pools.  When entering a
C function we would indicate the memory manager to start adding all
newly allocated object to a pool of new live objects. When exiting the
C function, the pool would be emptied, so a new allocation that would
invoke the garbage collector could collect those objects if they don't
have a live reference anymore.

The live pool can be a block with an increasing =objcount=.
=open_live_pool= and =close_live_pool= save and restore the current
pool =objcount=, like mark and free in Pascal.  There's no need to
unwind-protect the closing of the live pool, it'll be englobed
automatically when a surrounding =close_live_pool= is called. (cf. §
`Non-Local Exits from C Function`)


#+BEGIN_SRC c
Ref fun(Ref par){
   uword pool=open_live_pool();
   add_to_live_pool(par);
   Ref temp=cons(par,NIL_Symbol); /* temp is in the live pool,
                                     so it won't be collected */
   garbage_collect();
   Ref res=cons(par,NIL_Symbol);    /* temp and other are live */
   close_live_pool(pool);
   /* Note: temp and res are not live anymore. */
   return res;}

Ref gun(void){
   uword pool=open_live_pool();
   Ref n=random(I(10));
   Ref res=cons(I(3),add_to_live_pool(fun(n))); /* fun::res is now live again! */
   /* fun::temp  is dead, and may have been garbage collected. */

   variable_set(S(FOO),res); /* new reference */
   close_live_pool(pool);
   /* gun::res is live (for the FOO var reference) */}
#+END_SRC

* Environments
** Environment Kinds

There are two kinds of environments:

- compilation-time (minimal-compilation) ie. macroexpansion-time
  &environment environments.  The compilation-time environments are
  used while analysing (macroexpanding) the source code, to record the
  lexical objects used by inner macros and minimal-compilation.

- run-time environments.  The run-time environments are parts of the
  =Frame= that is stored on the heap, to be referenced by closure, and
  that contain the local lexical variable and function bindings.


The =COM.INFORMATIMAGO.BOCL.ENVIRONMENT= package implements
compilation-time environments, and produces from them the information
required to generate the run-time environment meta-information.  The
=Frames= are allocated by the interpreter =KERNEL:EVAL= function for
the special-operators requiring them.

The minimal-compilation process should store with the generated
special-operator forms, the run-time environment meta-information.

Operators openning a new =Frame=:

| Operator       | CT/RT             | Scope           | Binding    | Exit                       |
|----------------+-------------------+-----------------+------------+----------------------------|
| UNWIND-PROTECT | Frame             | dynamic         | cleanup    | Execute cleanup            |
| HANDLER        | Frame             | dynamic         | handlers   | Remove handlers            |
| RESTART        | Frame             | dynamic         | restarts   | Remove restarts            |
| CATCH          | Frame             | dynamic         | object     | Remove catch object        |
| BLOCK          | CT, Frame         | lexical         | blocks     | Remove scope (blocks)      |
| TAGBODY        | CT, Frame         | lexical         | tags       | Remove scope (tags)        |

** Compilation-time Environments

At compilation-time (macroexpansion-time), the compiler uses an
environement objects to record the objects visible in the lexical
scopes. Those environments are passed to compiler-macros, macros
functions, and other functions that take a &environment parameter.

These environment objects record:

- local functions (flet, labels, macrolet),
- local variables (lexical and dynamic binding, symbol-macrolet),
- declarations
- block names,
- tagbody tags,

They don't record CATCH objects, since they are computed dynamically.

Additionnaly, the compiler (minimal-compiler) manages a global
environment where the global definitions are recorded:

- global functions,
- global macros,
- global symbol-macros,
- global compiler-macros,
- global special variables (dynamic binding),
- global constant variables (no binding),

These compilation-time environments let the compiler know what run-time
environment will exist and map the local variables and local functions
to run-time environment and indexes.

** Global Environment

The global environment is reifed as an =ENVIRONMENT= object.

The defining standard macros registers the definitions in this global
environment object.  (When not running in bocl, the host environment
is not used).

** Run-time Environments

The run-time environments can be stored partially in automatic Frames
(in =evale()=) and on heap =VectorOfObject= for closures.

The Frames are structures allocated on the stack in =evale()=, and
used mainly to manage non-local-exits.

There are specialised frames for:
- unwind-protect,
- block,
- catch,
- tagbody,
- condition handler,
- restart.

Dynamic scopes also use a unwind-protect Frame to cleanup the dynamic
bindings.

We could add Frames for lexical bindings, and for local functions.
Those frames would allocate the storage for lexical local variables
and local functions on the heap in a =VectorOfObject=.

The local variables and local functions would be mapped to indexes
into these =VectorOfObject=.

** Non-Local Exits from C Functions

The Non-Local Exits are implemented in C using =setjmp=/=longjmp= in
linked =Frame= structures, allocated on the C stack in the =evale()=
function.  The =Frame= structures are also referenced from the
=environment= objects.

#+BEGIN_SRC lisp
(defun f (exit)
  (unwind-protect
       (funcall exit 42)
    (print '(exiting from f))))

(block garbonzo
  (unwind-protect
       (f (lambda (r) (return-from garbonzo r)))
    (print '(exiting from garbonzo))))

(exiting from f)
(exiting from garbonzo)
--> 42
#+END_SRC

* Minimal Compilation & Eval

We implement in C an interpreter =KERNEL:EVAL= function.  However, to
simplify the interpret, and therefore the C code, some special
operators will be implemented as macros (in meta-circular fashion), so
that only a reduced set of special operators need to be implemented in
=KERNEL:EVAL=.

** Minimal Compilation

The Minimal Compilation is a process implemented by =CL:COMPILE= and
=CL:COMPILE-FILE=, =CL:EVAL= and =(CL:COERCE sexp 'FUNCTION)=.

It consists into walking the code, and macro-expanding it.  The
resulting code will only contain function applications and
special-operators (those not implemented as macros).

=CL:COMPILE-FILE= can save the macro-expanded forms into fasl files,
that can be loaded as "compiled" forms, and directly interpreted.

Loading lisp source files, will require a Minimal Compilation phase,
before interpretation.

In addition to macro-expansion, Minimal Compilation must deal with:

- =EVAL-WHEN=
- =LOAD-TIME-VALUE=

*** CL:EVAL

=CL:EVAL= must perform Minimal Compilation on the source form given in
argument, to be interpreted by =KERNEL:EVAL=.

#+BEGIN_SRC lisp
  (defun CL:EVAL (form)
    (funcall (compile nil `(lambda () ,form))))
#+END_SRC

=FUNCALL= will call =KERNEL:EVAL= on the compiled function.

** Special Operator FUNCTION

`(FUNCTION foo)`
`(FUNCTION (SETF foo))`

Find function `foo` or `(SETF foo)` in the environment: global or lexical.
Return the function closure.

`(FUNCTION (LAMBDA (...) ...))`

Create an interpreted anonymous function with the lambda expression.
Find the free variables and (local) free functions.

** Special Operator TAGBODY

Interpretation of a tagbody consists in interpreting sequentially the
forms in the body.  GO may jump to another section of the same
tagbody.  But in any case, unless GO is a tagbody-toplevel form, it
will involve a non-local exit, to find the tagbody concerned.


We keep the tags in the environments, and each tag keeps a reference
to its tagbodies and the other tags.

So the minimal-compilation of =TAGBODY= can compute a table mapping
tags to rest of tagbody forms, and substitute the =GO= tags.  We
encode both the =TAGBODY= form, and the tag index in the new =GO= tag.

This table can be stored in a  vector, so that the search for the tags
doesn't need  to be performed by  GO at run-time, but  is performed at
compilation-time.  At run-time, a local  =GO= can jump switch directly
to the entry  in the table, and  an inner =GO= can  find the =TAGBODY=
frame counting  them up, before jump  switch directly to the  entry in
the target =TAGBODY= table.

On architectures with w-bit words, we'll use (w/2)-2 bits to identify
the tagbody, and (w/2) bits to identify the tag.


#+BEGIN_SRC lisp

(defun parse-tagbody (body)
  (flet ((go-tag-p (object) (or (symbolp object) (integerp object))))
    (loop
      with sections = '()
      for form on body
      do (if (go-tag-p (car form))
             (push form sections))
      finally (return (coerce (nreverse sections) 'vector)))))

(cl:defun minimal-compile/tagbody (env form)

** =KERNEL:EVAL=

*** Non-Local Exits and Frames


cf. `5.2 Transfer of Control to an Exit Point`
http://www.lispworks.com/documentation/HyperSpec/Body/05_b.htm


Take for example, =BLOCK= and =RETURN-FROM=.

To process a =BLOCK= form, =KERNEL:EVAL= must set up and link a
dynamic frame identifying the block, and a return point, to itself, in
case a non-local exit occurs in the interpreted subforms (or called
built-in C functions).


The unwinding process calls longjmp from on Frame to the next Frame,
until we reach the target Frame (unwind_next_frame);

target_frame is the target frame of the non-local exit.

All the frames in the environment, from the first down to the
target_frame are long jumped to one another.

All but the =target_frame= is long jumped to with =non_local_exit_unwind=
result, and the =frame->target= set to =target_frame=.  The frame should
clean up, call =pop_frame()= itself from the environment, and call
=unwind_next_frame(itself)= to unwind the next frame.

The target_frame is long jumped to with non_local_exit_target
result.  It should pop_frame itself from the environment.


The basic control flow structure of an unwind-protect (or block,
catch, etc):

#+BEGIN_SRC C
  int result=setjmp(&frame.block_non_local_exit);
  switch(result){
    case non_local_exit_initial:
        push_frame(&frame,environment);
        BODY();
        pop_frame(&frame,environment);
        break;
    case non_local_exit_unwind:
        /* non-local-exit to an upper frame,
        but we get a chance to unwind here */
        CLEANUP();
        pop_frame(&frame,environment);
        unwind_next_frame(frame);
        break;
    case non_local_exit_target:
    default:
        /* non-local-exit, were' the target */
        CLEANUP();
        pop_frame(&frame,environment);
        break;}
#+END_SRC

In the C KERNEL:EVAL function, this control flow is abstracted with
the =UNWIND=, =UWBODY= and =UWCLEANUP= macros.


And the basic control flow structure of a non-local exit:

#+BEGIN_SRC C
  Frame* target_frame=find_???_frame(name,environment);
  if(NULL==target_frame){
      error("No ??? named ~A",name);}
  COMPUTE_RESULT();
  /* Non-local exit: */
  Frame* frame=pop_frame(NULL,environement);
  frame->target_frame=target_frame;
  unwind_next_frame(frame);
#+END_SRC

With =unwind_next_frame=:

#+BEGIN_SRC C
_Noreturn unwind_next_frame(Frame* frame){
    /* Unwind one frame */
    non_local_exit_t exit=((frame->next==frame->target)
                           ?non_local_exit_target
                           :non_local_exit_unwind);
    frame->next->target=frame->target;
    longjmp(frame->next->non_local_exit,exit);}
#+END_SRC

** =COMPILE-FILE= and fasl files

The implementation architecture is that of:

- a  minimal-compiler  that expands  the  macros  and performs  a  few
  transformations on the resulting form.

- a KERNEL:EVAL interpreter that executes directly the minimally
  compiled form.

Note: KERNEL:EVAL may not be able to evaluate a pure source form
(yet). In anycase, this would be much slower (macroexpansions).

The minimal-compiler is invoked automatically by each defining form
(=defun=, =defmacro=, =function=, etc).

=COMPILE-FILE= will process forms read from a source file, applying
the minimal-compilation of each toplevel form.  Some of those forms
will be evaluated in the compilation environment (eval-when
:compile-toplevel).  The other minimally-compiled forms are saved in a
fasl file, which therefore a lisp file containing only special
operators and function calls.
